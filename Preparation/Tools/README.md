# The tools, and which one answers which question

Fifty-four diagnostic tools sit in `Diagnose\`, forty-six of them with a
build script beside them. This page is their index: the way to find the
right one without already knowing it exists.

Every tool prints its own usage when started without arguments, and every
one carries a header comment saying why it was written. That header is the
authority; this page only points at it.

## Building

`Diagnose\<b*.bat>` - run it, it builds in place. Every script is relative to
its own folder, so a fresh clone builds them. They need Visual Studio with
the C++ workload; the path to `vcvars` is the one absolute thing in them.

`bmap.bat` and `btrg.bat` are no exception: every path in them is the
`%~dp0` form as well.

**The one prerequisite, said once here:** the `vcvars` line names a specific
Visual Studio installation. If yours sits elsewhere - a different edition, a
different major version - that single line in each script is what to change;
nothing else in them is machine-dependent. Two of the forty-eight `b*.bat` are
not tool scripts at all: `be.bat` builds the engine and `bshader.bat` compiles
the shaders. `bshader.bat` has no `vcvars` line but needs `fxc.exe` of the
Windows SDK (an optional component of the same workload, installed by
default), which it looks for in the two `Windows Kits\10\bin` folders under
`Program Files` and `Program Files (x86)`; it is needed only when a `.hlsl`
changes - a build of the published tree runs `be.bat` without it, because the
tracked `.inc` match their stamps.

Eight tools have no script: CornerCheck, DinoCheck, FaceCheck, GeomTest,
TR3FetchCheck, TR3SoundCheck, TriggerCommands, WinCheck. Their headers
carry no build line. They build with the command line of CameraCheck's script
(`bcc.bat`: the tool, `Tr5Level.cpp` and zlib) with their own name substituted;
TriggerCommands adds `DataFolder.cpp`, and DinoCheck, TR3FetchCheck
and TR3SoundCheck take `Tr3Source.cpp` and `DataFolder.cpp` in place of
`Tr5Level.cpp`.

One header beside them is shared rather than a tool: `VisInput.h`, which RoomProbe
and TrgProbe both include for the visibility walk's inputs out of a `.TRC`.

`ModernTest` and `MenuTest` also read engine sources at run time, by their path from
their own EXE's folder (`Diagnose\`) and then from the working directory, so a start
from any folder gives the same counts.

The tools that read the player's game files look for them by default in a folder
named `Tomb5 Steam Version` at the root of the clone (`..\..\..\Tomb5 Steam
Version\data\` from `Diagnose\`, as `InterpTest`, `LipsTest` and `CutseqProbe` name
it): the player's own copy of the installation, which git ignores and the
repository does not carry. A path on the command line takes its place.

The rows of `ModernTest`, `MenuTest`, `InterpTest` and `LipsTest` below describe a
selection of their groups. Every group and its checks stand in the suite's own
source; the counts are the ones the run prints.

CornerCheck, GeomTest and WinCheck were written in a scratch folder outside
the clone, and their build scripts stayed behind on purpose: those carried
absolute paths, and two of them were even named `bcc.bat` and `bwc.bat`,
which belong to CameraCheck and BalanceWriteCheck here. All three take the
same command line as CameraCheck's script - `Tr5Level.cpp` plus zlib, nothing
else - with their own name substituted.

## By subject

**Levels, rooms, sectors**
| Tool | Script | What it answers |
|---|---|---|
| `ItemCheck` | bip | every item with OCB, flags, room and angle - the first thing to run on "why is this item behaving oddly". |
| `RoomCheck` | brp | room flags and flipmap partners. |
| `InfoCompare` | bic | compares what `Rando::levelInfoFromLevel` reads out of a `.trc` against the old `level_<name>.json`, field by field. Written to prove the 45 MB of exports could go; keep it for the next time someone doubts the level file is the better source. |
| `SectorCheck` | bsek | one sector in plain text, including the raw eight FLOOR_INFO bytes. |
| `FloorCheck` | bb | floor heights and slopes, the rule set behind item placement. |
| `FaceCheck` | - | which drawn faces cover a sector. |
| `CornerCheck` | - | proof for `cornerFloor` / `cornerCeiling`: every horizontal vanilla face that covers one sector must sit corner for corner on the height the floordata computes. Run it after any change to the floordata reading - it is the only independent witness there is. |
| `WinCheck` | - | holds `wallWindow` against the 32-byte view windows Core shipped. A window only ever clips, so when the two differ the direction is what matters: too large costs nothing, too small blacks out part of the neighbouring room. |
| `GeomTest` | - | tries `buildRoomGeometry` on one room and reports what came out - face count, triangles, bounding box, degenerate faces. The tool for a room that has no drawn surface at all. |
| `LevelDiff` | bld | two levels compared block by block. If everything but the images is byte-equal, only textures were exchanged. |
| `LevelBuild` | bbw | applies a patch JSON to a level - how the hand-built test levels are made. `-hdm` writes the run's `.hdm` sidecar beside the result as the randomizer does: a copied slot's `donor` line and a shrunk copy's `scale` line, so `ModelProbe -hdm` and the engine read the test level as a run's. |
| `FixCheck` | bfc | applies LevelFix and saves the result, so the repairs can be looked at in trview - and a repaired view window drawn by RoomProbe, with `-roombox` on the folder the result was saved to. For a one-shot entry (`TriggerOneShot`) it checks the result itself: `FOUND` lists the triggers it reaches with sector, item and setup word before and after, `SET` reads the saved file back and walks the room on its own, `BYTES` compares source and result byte by byte (only the setup words' high bytes may differ). Ends with `HOLDS`, or `FAILS` and exit code 2 on any warning or failed check. |
| `TriggerCommands` | - | counts which trigger commands occur in a level. |
| `CameraCheck` | bcc | the fixed cameras with their flags. |
| `TexRec` | btx | texture pages and texinfos. |
| `HdmDump` | bhdm | the HD markers: `data[3]` of the level header with its meaning, and the `.hdm` sidecar beside the file. Doubles as the reference reader for the sidecar grammar - the engine's own reader has to answer the same way on the same file. Reads version 1 and version 2; a version 2 file carries `cut` lines, one axis-aligned box in world units per opening the run made, and they are printed with the span of each axis so the box can be checked by eye: exactly one of the three spans is 1024, and that one is the opening's normal (2 x 512 over a raw box that is flat there); the other two are the opening's own size less 2 x 128, the inward step taken to keep the cut clear of the opening's edge. The `item` lines, the items the run added by their index in the level file, come out as one `items` list and their count in the `sidecar` line. A `scale <slot> <num> <den>` line, a copy the run shrank (the drone, #289), prints as `scale slot <n> x <num>/<den>` with its decimal. Run it on a finished level; a vanilla one says "no markers", which is what the engine reads too. |

| `RootProbe` | broot | the ROOT OFFSET of an animation - `frm[6..8]`, the three shorts the draw translates by after the item's own rotation - and what the 60 FPS in-between frame draws it as. Prints the animation table row with the fields `AnimCmd` does not read (where it continues, and at which FRAME), every animation command including type 1 `TranslateItem`, where each state change really goes, every key frame's offset, and then the WRAP REPLAY: three logic ticks either side of the wrap with the drawn root at thirty hertz, and the tween frames both as the engine drew them before the interpolation fix and as it draws them now.<br><br>It exists because a ladder carries its whole vertical travel inside those offsets and moves `item->pos` only once, at the wrap, so "the picture is continuous at thirty" is a statement about two numbers ADDING UP - and nothing else in the toolbox could read either of them. It also prints, for the tween frame the rule really reaches, the whole `INTERPLOG root lara` line that frame will produce in a `-log` run, in all three axes - because writing that line out by hand from the key table beside it is how a wrong x and z first got caught. `-grab <from> <to> [posStep]` does the same for a change from one animation to another, which is what the ladder grab is; where the change is the animation's own wrap, `posStep` defaults to that animation's `TranslateItem` rather than zero, so a bare `-grab 172 173` still shows the grab as the engine draws it. `-sweep [least]` walks every wrap and `jump_anim_num` change of Lara's whole animation table, prints the offset step, the leaving animation's own `TranslateItem` (or none) and the verdict - paid in full, paid in part, not at all - for every axis whose offset step is at least `least` units (default 8), and is the table the check itself reads. Its summary counts the invariant itself, beside the count that stop blending, instead of leaving the zero to be read off the per-row columns: how many rows draw OUTSIDE the segment from the frame's own offset to today's draw - further out or the other way - which must read 0, and does (0 of 433 in ANDREA1, 0 of 352 in JOBY5). That is the form of the invariant that can be violated; "blends where today's does not" is dead here, because a row only enters the sweep when an axis moves at least `least` units and today's half-blend then always lands off the frame's own offset. A tween row that rule K6 ACCEPTED says `(accepted frame - not drawn)` rather than `(rule does not fire)`: neither rule is asked on an accepted frame, so the two rows' differing numbers there are the arithmetic of a blend nobody performs. The `step=`/`kept=` line of the wrap and grab tables also prints `d_off=`, `today=` and `narrowed=` in words (`blends` or `stands down`) and `worst=`, the difference the two pictures grow to over a whole tween - which is the largest one, not the alpha-0.5 pair printed beside it; the verdict is printed in words so that it is never inferred from the absence of a marker on cases where neither rule fires. |
| `AnimProbe` | bap | cross-check of `Tr5Level::laraAnimUsable`. |
| `LaraAnim` | bla | which of Lara's animations a level REALLY carries. Levels stub the ones they do not need, and a stub is not a missing entry - it looks present. |
| `BoneCheck` | bbone | a slot's bone tree, or two compared - whether one slot's meshes fit another slot's animations (the brawler's two donors, JOBY2's slot 439 and joby3's chef 87: `0 of 14 bones deviating`). |

**Savegames**
| Tool | Script | What it answers |
|---|---|---|
| `SaveDiff` | bsd | two savegames compared **field by field, by name**. Prints `IDENTICAL` when the files match to the byte, otherwise one line per differing field with both values - so "played four seconds longer" (`Game.Timer`, the clock, Lara's position) is told apart at a glance from "the game ran differently" (`Level.Kills`, the ammunition counts, `Lara.air`). Written for the frame-rate proof: the draw path has its own RNG that the simulation never reads, so the same seed and the same inputs must arrive at the same state at 30 and at 60 frames a second, and a savegame is that state written down. The recipe is in `docs/Engine-Manual.md` under *Frame rate*.<br><br>Takes every offset from the engine's own `global/types.h` with `offsetof`, so it cannot go stale - and is therefore built **x86**, like `BalanceCheck` and `RoomProbe`: the structs are `#pragma pack(1)` but carry pointers, and a pointer is four bytes in the engine. What it cannot name is the savegame *stream* inside `SAVEGAME_INFO::buffer` - that is what `WriteSG` (`game/savegame.cpp`) packed in a variable-length, conditional order - so those are reported as differing byte runs with their offset. |
| `InterpTest` | bit | the ARITHMETIC of the 60 FPS interpolation, checked with no game and no device. Lara's key frames and her bone table are read at run time, read only, from the player's own `ANDREA1.TRC`: `InterpTest [path of data\ANDREA1.TRC]`, or, with no path, the file in the game folder beside the repository, looked for from the EXE's folder and then from the working folder; a table whose animation's frame size does not match is refused, so another level is not taken for it. It **includes the engine's own `TOMB5 Code\TOMB5\game\interpolate_math.h`** rather than a copy of it, so it cannot drift from what the engine does: a change to the lerps or the snap thresholds is a change this test sees. 754 checks — the count the run itself prints, and the one at the end of this row — the short-angle lerp over a sweep of 16,256 angle pairs (that every one turns the SHORT way round and lands within a unit of halfway, with the 128 exact half-turns stepped over and asserted on their own), the position lerp over the whole coordinate range of a level, the snap thresholds against the engine's own speeds (a terminal fall interpolates, a sector-wide teleport does not), that a Manhattan sum is never smaller than the true distance, and the cadence: `framecount` and `DrawPhaseGame`'s alpha rule run for a simulated minute at both frame rates and through a hitch - 1800 logic ticks either way, exactly half the frames interpolated at sixty, none at thirty, every drawn step exactly half a tick.<br><br>It exists because a short angle blended the LONG way round is invisible almost all the time and looks like a rendering glitch when it is not: one enemy, facing roughly south, spinning backwards for half a tick on every second frame. That has to be proven at the wrap, and play cannot be made to put a body on the wrap at will. `counters` is a simulated wall-clock second at both rates with the engine's own tween-frame rule, asserting that a guarded counter steps thirty times in BOTH modes (not sixty), that the nine-step screen fade spans the same nine ticks - 2n-1 presents at sixty, because it begins and ends on a live frame - and that at `fps_mode 0` not one frame is ever an in-between frame. One thing the two picture tools cannot make up: they have no classic level, so
`RoomProbe` cannot read a room's flags or its roomlets. `-underwater` and `-shimmer` are
therefore switches rather than answers, and `-shimmer` - and `-water` with it - lights or
wobbles the WHOLE room (the selector is aimed at the vertex's constant fourth
flag byte) where the engine touches only the vertices its own predicate marked.
That difference is large: over the vanilla levels the classic water set is 0 to
188 vertices per level, so a `-water` picture over-reports on purpose. The
picture proves the arithmetic and the animation; which vertices get it is the
engine's business. The scroll and wind are NOT in
that class - they are marked in the `.TRG` itself, so what the tool draws there
is what the engine draws.

`bshader` is not a tool but a build step of its own: it runs `fxc` from the
Windows SDK over `specific\hd\hd_shader\*.hlsl` and writes the bytecode next to
it as `.inc` byte arrays. The engine's project has **no** shader compile step.
Both the `.hlsl` and the generated `.inc` are checked in — GPLv3 wants the
source that produced the bytecode to sit beside it.

**`be.bat` checks that for you.** Every `.inc` carries
the MD5 of the `.hlsl` it came from on its last line (`bshader.bat`, `:stamp`),
and the five whose shader includes another `.hlsl` (glow and water look
include `hd_room.hlsl`, the shadow caster `hd_model.hlsl`) carry that file's
MD5 on the line before (`:incstamp`). `be.bat` compares all 39 `.inc` before
it builds; where they differ it prints
`be: regenerating shaders - ... out of step with the HLSL`, runs `bshader.bat`
itself and only then builds, and it refuses to build at all if that fails. A
**content** stamp and not a file date, because a fresh clone gives every file
the same date and a date guard would then either cry wolf or say nothing at
all.

**`be.bat` also compiles the whole engine on every run** (`msbuild
/t:Rebuild`, about half a minute), never only what `msbuild` takes for
changed. `msbuild` goes by file dates: a source file put back with a date
older than its object file - a copy that keeps the date, an archive unpacked
over the tree - is passed over although its content is new, and the link
joins object files of two states of one header. Such a binary compiles, links
and can die at once. The full build leaves no such mix possible, and it gives
every binary its own build time (`winmain.cpp` writes it as the first line of
a `-log` run).

**And a content stamp has its own trap.** An MD5 is taken over bytes, and
line endings are bytes: with
git's Windows default the `.hlsl` came out of a fresh clone with carriage
returns the stamped file never had, so the guard fired on shaders that were
perfectly in step, rebuilt them, and left two tracked files modified in a
clone nobody had touched. Worse, the two pairs disagreed with each other -
one had been stamped over LF, the other over CRLF - so on any machine one of
them was lying. The fix is one rule in `.gitattributes`, `eol=lf` for
`**/hd_shader/*.hlsl` and `*.inc`, so every machine hashes the same bytes;
the four `.inc` were regenerated over LF sources and proved to differ from
their predecessors in the stamp line alone. Nothing in the scripts changed.
If you edit a shader, keep its file LF. It exists because a shader source
once changed without `bshader` being run, and the build shipped with its
source and its picture disagreeing - nothing in the tree could say so, and only
the running game showed it. Running
`bshader.bat` by hand still works and is still the right thing to do while
iterating on a shader; the guard is the net underneath.

## The other half: the engine tells you things too

The engine writes nothing unless it is started with `-log`. `Log.bat` in the
release package does exactly that, which is why it is in there. The seams
below are permanent - they are not debug leftovers to be tidied away, they
