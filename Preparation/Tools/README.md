# The tools, and which one answers which question

Fifty-two diagnostic tools sit in `Diagnose\`, forty-three of them with a
build script beside them. This page is their index: the way to find the
right one without already knowing it exists.

Every tool prints its own usage when started without arguments, and every
one carries a header comment saying why it was written. That header is the
authority; this page only points at it.

## Building

`Diagnose\<b*.bat>` - run it, it builds in place. Every script is relative to
its own folder, so a fresh clone builds them. They need Visual Studio with
the C++ workload; the path to `vcvars` is the one absolute thing in them.

`bmap.bat` and `btrg.bat`, the two that link the most engine files, are no
exception: every path in them is the `%~dp0` form as well.

**The one prerequisite, said once here:** the `vcvars` line names a specific
Visual Studio installation. If yours sits elsewhere - a different edition, a
different major version - that single line in each script is what to change;
nothing else in them is machine-dependent. Two of the forty-five `b*.bat` are
not tool scripts at all: `be.bat` builds the engine and `bshader.bat` compiles
the shaders.

Nine tools have no script and are built by hand from their header comment:
BoneCheck, CornerCheck, DinoCheck, FaceCheck, GeomTest, TR3FetchCheck,
TR3SoundCheck, TriggerCommands, WinCheck.

CornerCheck, GeomTest and WinCheck were written in a scratch folder outside
the clone, and their build scripts stayed behind on purpose: those carried
absolute paths, and two of them were even named `bcc.bat` and `bwc.bat`,
which belong to CameraCheck and BalanceWriteCheck here. All three take the
same command line as CameraCheck's script - `Tr5Level.cpp` plus zlib, nothing
else - with their own name substituted.

| `RootProbe` | broot | the ROOT OFFSET of an animation - `frm[6..8]`, the three shorts the draw translates by after the item's own rotation - and what the 60 FPS in-between frame draws it as. Prints the animation table row with the fields `AnimCmd` does not read (where it continues, and at which FRAME), every animation command including type 1 `TranslateItem`, where each state change really goes, every key frame's offset, and then the WRAP REPLAY: three logic ticks either side of the wrap with the drawn root at thirty hertz, and the tween frames both as the engine drew them before the interpolation fix and as it draws them now.<br><br>It exists because a ladder carries its whole vertical travel inside those offsets and moves `item->pos` only once, at the wrap, so "the picture is continuous at thirty" is a statement about two numbers ADDING UP - and nothing else in the toolbox could read either of them. It also prints, for the tween frame the rule really reaches, the whole `INTERPLOG root lara` line that frame will produce in a `-log` run, in all three axes - because writing that line out by hand from the key table beside it is how a wrong x and z first got caught. `-grab <from> <to> [posStep]` does the same for a change from one animation to another, which is what the ladder grab is; where the change is the animation's own wrap, `posStep` defaults to that animation's `TranslateItem` rather than zero, so a bare `-grab 172 173` still shows the grab as the engine draws it. `-sweep [least]` walks every wrap and `jump_anim_num` change of Lara's whole animation table, prints the offset step, the leaving animation's own `TranslateItem` (or none) and the verdict - paid in full, paid in part, not at all - for every axis whose offset step is at least `least` units (default 8), and is the table the check itself reads. A tween row that rule K6 ACCEPTED says `(accepted frame - not drawn)` rather than `(rule does not fire)`: neither rule is asked on an accepted frame, so the two rows' differing numbers there are the arithmetic of a blend nobody performs. The `step=`/`kept=` line of the wrap and grab tables also prints `d_off=`, `today=` and `narrowed=` in words (`blends` or `stands down`) and `worst=`, the difference the two pictures grow to over a whole tween - which is the largest one, not the alpha-0.5 pair printed beside it; the verdict is printed in words so that it is never inferred from the absence of a marker on cases where neither rule fires. |

**Savegames**
| Tool | Script | What it answers |
|---|---|---|
| `SaveDiff` | bsd | two savegames compared **field by field, by name**. Prints `IDENTICAL` when the files match to the byte, otherwise one line per differing field with both values - so "played four seconds longer" (`Game.Timer`, the clock, Lara's position) is told apart at a glance from "the game ran differently" (`Level.Kills`, the ammunition counts, `Lara.air`). What it cannot name is the savegame *stream* inside `SAVEGAME_INFO::buffer` - that is what `WriteSG` (`game/savegame.cpp`) packed in a variable-length, conditional order - so those are reported as differing byte runs with their offset. |

The spin is also walked over the 65536 wrap four times with not one long-way frame, and the slide is walked through three whole turns of the ring with the reset - `objlistmovement` back to 0 and `curobjinlist` moved on - never blended halfway back. A settled braid reads zero and stays there; the regimes that read anything else are the ones the game had. Both torso anchors are run, the ordinary one and the Russia/bunhead one. Default 60 steps, a second of game time. The pack is a **box** and the "in a pack" column is measured against it whatever the regime, so the sphere regimes say how far into the backpack the braid walks under them. `-classicroot` draws the braid from the classic anchor, which is the picture before the pack became a box; **`-braidrest [regime]` draws the braid where the SIMULATION leaves it** rather than in a studio pose, which is the only way a still picture can show whether the plait lies on the pack or in it (no number: the regime the engine ships).<br><br>**`-braidanim [<n>]` runs the same chain under a REAL animation**: the bind pose has no anchor motion at all, so this reads the level's own animation table, decodes the frames Lara really wears and rebuilds all eight collision spheres and the braid root from them once per game frame - the same node walk, the same skips through the packed rotation stream, the same frame blending, the positions truncated to longs afterwards, and the floor clamp in (a braid 336 units long hanging from a head 251 units up reaches through the ground she stands on; `-nobraidfloor` takes it out). One row per physics variant - the classic body alone, the pack as `-braidsim` ships it, and three ways of softening it - counting the TIP's travel per frame in the same four buckets a play test's `HAIRLOG` is counted in, plus the shortest the chain ever got and the worst one-frame change of a link's YAW. Then a second table: the DRAWN bone's twist under five roll rules, which is how it was found that the braid stands still to within a unit and spins half a turn on one frame in eight. Repeat the switch for more animations; with no number it runs 103 (breathing on the spot), 0 (the run loop) and 1 (the walk loop). There is a **`head` column** as well - `tr5`, `hair` or `outfit`, and in brackets who decided: the bundle the body was drawn for (`origin`), the mod's own `outfit.txt`, or the default. The very same scan the engine and the randomizer run - `hd_wardrobe.cpp` is compiled into all three - so a key this prints is a key the game will find. `-outfit` takes a key as well as the old spellings.<br><br>**Two more switches for the inventory ring.** `-invrot <x> <y> <z>` puts the item's own three angles from `inventry_objects_list` on the model exactly as `phd_RotYXZ` does, so that a picture out of this tool is what the INVENTORY RING shows and not what the item's own frame holds - without it the two are nothing alike, which is the gap an earlier ring rendering fault fell into (`-name EXTRA_PISTOLS_ITEM -invrot 0x4000 0xAD4C 0xBD40` draws the two crossed pistols the player sees). `-pagelist` prints every slot of the page cache after a `-lara` build - the key, where the `.DDS` was read from, the size it was decoded to and its bytes - so two runs diff against each other and the cost of a second outfit is a set difference instead of a guess.<br><br>**Three more for reading a raw model file.** `-rigid` loads a `-name` model the way the RING loads a mod's `<BASE>_OPTION`: ONE node, every vertex rigid on it. It is not a nicety - a file whose geometry sits on nodes other than 0 draws NOTHING through the ordinary `-name` path, because a bare `-name` run has no mesh tree to place those nodes, and that is why a face-on render of `UZI_OPTION` (27449 vertices on nodes 1 and 2, one gun each) came out an empty magenta picture. `-axisview` turns the model so that its own vertex cloud's principal plane faces the camera - axis 0 onto x, axis 1 onto y, the flattest onto z - which is the picture that answers "what SHAPE is this file", the question the ring's fit rests on; with `-yaw 90` and `-pitch 89` beside it you get all three orthogonal views of the model in its own frame. It wants `-tr3` for the root - the bundle is that folder's parent, the same step the engine takes. It reads all three games, where `TR3Peek` reads TR3 alone. The small square is the one that can be read: at a low camera the big outline's near edge stands well in front of the point the rule is about, so a model resting exactly on the plane still shows a gap there. Take it with a low camera; `-pitch 4` reads well, `-pitch 55` shows a crossed pair from above. The frame matters: an item is NOT drawn in the pose its file is modelled in - six of ANDREA3's eighteen pickups carry a turn on node 0 that is not a plain yaw, and `UZI_ITEM`'s stands the model on its head - so every other switch's picture is the bind pose and this one is not. `-pose`, `-invrot` and `-axisview` are left out of a floor picture for the same reason. **The rooms in space** is a question the two tools
answer together, and they must answer it the same way. `TrgProbe -roomspace
-classic <folder holding the classic .TRC>` reads the classic level and the
`.TRG` side by side and prints the room boxes, the OVERLAP list - whose art
stands inside whose room, with no portal between the two - the overhang
histogram by distance and by side, and the hollow groups; `-room <n>` takes one
room apart (box, portals, vertical links, whose art is inside it), `-statics` /
`-slot <n>` every static mesh with how much art stands in its box, `-slack` and
`-deep` move the two thresholds so that a rule can be re-measured rather than
believed, and `-near <x> <y> <z> <radius>` says whose art stands at a given
place in the world and how far that art is from its own room's box - which is
how "a tower that is in no room's box" was turned from a guess into a number.
`RoomProbe -roombox <same folder>` hands the engine's renderer the same room
boxes AND the same overlap list the game hands it and then prints what its
build made of them, so the two listings can be held against each other line for
line; `-window all|open|intruding` draws one half of every group, `-clipgroup
<group> <l,t,r,b>` puts a scissor round ONE group (which is what a portal
window really is, and what the whole-scene `-scissor` cannot do), and `-tround
<group> <l,t,r,b>` draws one group the OLDER way - its inside
half inside the rectangle, its overhang whole - which is the "before" picture
next to the current one.

One thing the two picture tools cannot make up: they have no classic level, so
`RoomProbe` cannot read a room's flags or its roomlets. `-underwater` and `-shimmer` are therefore
switches rather than answers, and `-shimmer` - and `-water` with it - lights or
wobbles the WHOLE room (the selector is aimed at the vertex's constant fourth
flag byte) where the engine touches only the vertices its own predicate marked.
That difference is large: over the vanilla levels the classic water set is 0 to
188 vertices per level, so a `-water` picture over-reports on purpose. The
picture proves the arithmetic and the animation; which vertices get it is the
engine's business. The scroll and wind are NOT in
that class - they are marked in the `.TRG` itself, so what the tool draws there
is what the engine draws.

`bshader` is not a tool but a build step of its own: it runs `fxc` from the
Windows SDK over `specific\hd\hd_shader\*.hlsl` and writes the bytecode next to
it as `.inc` byte arrays. The engine's project has **no** shader compile step.
Both the `.hlsl` and the generated `.inc` are checked in — GPLv3 wants the
source that produced the bytecode to sit beside it.

**`be.bat` checks that for you.** Every `.inc` carries
the MD5 of the `.hlsl` it came from on its last line (`bshader.bat`, `:stamp`)
and `be.bat` compares the two before it builds; where they differ it prints
`be: regenerating shaders - ... out of step with the HLSL`, runs `bshader.bat`
itself and only then builds, and it refuses to build at all if that fails. A
**content** stamp and not a file date, because a fresh clone gives every file
the same date and a date guard would then either cry wolf or say nothing at
all.

**And a content stamp has its own trap.** An MD5 is taken over bytes, and
line endings are bytes: with
git's Windows default the `.hlsl` came out of a fresh clone with carriage
returns the stamped file never had, so the guard fired on shaders that were
perfectly in step, rebuilt them, and left two tracked files modified in a
clone nobody had touched. Worse, the two pairs disagreed with each other -
one had been stamped over LF, the other over CRLF - so on any machine one of
them was lying. The fix is one rule in `.gitattributes`, `eol=lf` for
`**/hd_shader/*.hlsl` and `*.inc`, so every machine hashes the same bytes;
the four `.inc` were regenerated over LF sources and proved to differ from
their predecessors in the stamp line alone. Nothing in the scripts changed.
If you edit a shader, keep its file LF. It exists because a shader source
once changed without `bshader` being run, and the build shipped with its
source and its picture disagreeing - nothing in the tree could say so, and it
took a play test to find. Running
`bshader.bat` by hand still works and is still the right thing to do while
iterating on a shader; the guard is the net underneath.

## The other half: the engine tells you things too

The engine writes nothing unless it is started with `-log`. `Log.bat` in the
release package does exactly that, which is why it is in there. The seams
below are permanent - they are not debug leftovers to be tidied away, they
are how a player's crash report becomes usable.

| Symptom | Seam | What it prints |
|---|---|---|
| the wrong sound plays | `SFXLOG` | which sample really played, and which anim command asked for it |
| an enemy is invisible | `SLOTLOG`, `SKIPLOG`, `MESHLOG`, `CLIPLOG` | the four separate reasons: no free AI slot, control skipped it, no mesh, clipped away |
| ...and if it is the clipping | `CLIPDETAIL` | the actual window and the camera it was measured against |
| an item is in the wrong place, or vanishes | `ITEMLOG` | slot, room, OCB, flags per item at load |
| ...and something moves it later | `ITEMWATCH` | who wrote which room number, and when |
| the outfit looks wrong, a limb is misplaced | `SKINLOG` | the skin's bone stack |
| the first-person view sits wrong | `FPHEAD`, `ALTERFOV` | the head bone per frame, and the field of view |
| an HD object or Lara is wrong, or classic when it should not be | `HDLOG` | per level: which slot got which model and why it was refused; Lara's outfit, her parts and the reason for a classic one. Per level's first HD frame: `itemcheck` and `lightcheck` for the objects, `laracheck` and `braidcheck` for Lara |
| it stuttered, or dropped under the frame rate | `FPSLOG` | one line per second: frames presented, the longest gap, and `logic_ticks=` - what the SIMULATION ran, which must stay 30 whatever the frame rate is |
| ...and *why* it stuttered | `PROFLOG` | the same second split into the fifteen phases of a frame (logic, room walk, HD rooms, HD objects, buckets, sort, the wait for the slot, `Present`), mean and worst; plus one line for **every** frame that missed its slot with all its phases, and one `first_frame` line per level |
| at *Frame rate 60* the motion is no smoother than at 30, or something jerks | `INTERPLOG` | one line per LOGIC second: how many frames were interpolated, how far Lara moved per drawn picture (must HALVE against a 30 Hz run over the same walk), how many things really moved, and every deliberate snap by cause - teleport, room jump, camera cut, cut scene |
| the first seconds of a level are rough | `WARMUP` | one line per load: how many texture pages and buffers were made resident before the first frame instead of inside it |

`SLOTLOG` also prints `MAX_LOT`, which is the number that decides how many
enemies can be active at once - see `Tomb5 Limits\Limits.txt`.
