Statue, Guardian, Hydra and CHEF.
(Boss-like special enemies/special cases with their own spawn/kill/structure logic - do NOT
simply swap against normal enemies, and do not put normal enemies into these slots. Own
category, own rules per entry. All 4 since cross-checked in the code, 2026-08-02.)
	1 Soldier Statue (TypeID 61 in trview, confirmed in Andrea3.trc) - stands visibly on the
	  floor, but on waking is moved 512 units back + 1024 units up, plays a stand-up/jump
	  animation and only then lands on the actual positioning tile. I.e. the start position
	  visible in the level is NOT the actual combat position - important when randomizing the
	  position (enough room for the 512/1024-unit shift + landing animation must exist at the
	  target).
	2 Guardian (guardian.cpp, TypeID not yet safely confirmed - documented in the code as a
	  boss with fixed script logic/LOS checks, no normal CreatureAIInfo). The actual enemy is
	  only the head with the 2 eyes. Belongs to a group of separate "Animating" objects
	  (in Andrea2.trc e.g. TypeID 438/439 "Animating 12"/"Animating 12 mip") that stand
	  around the head like spider legs / a cage: they unfold on waking (spider-like
	  animation), and on the head's death (through the 2 eyes) fold back together + explode.
	  ##  NOT SAFELY RANDOMIZABLE - code analysis (InitialiseGuardian, guardian.cpp:35-87):
	  the link to the cage parts does NOT run via proximity/room but searches the ENTIRE item
	  list of the level for the first item with a matching object_number (ANIMATING12 for the
	  center part, ANIMATING12_MIP with an exactly matching y_rot in 45-degree steps for the
	  8 cage segments, PUZZLE_ITEM4 for an additionally hidden part). No error handling when
	  no hit is found - the array entry stays uninitialized. This only works in vanilla
	  levels BECAUSE there is exactly one matching set there. With several guardians in the
	  same level, a changed item order, or a move into another level without exactly matching
	  companion objects, the head attaches to wrong/no parts.
	  RECOMMENDATION: exclude the Guardian completely from the randomizer pool (neither
	  source nor target) until the linkage in the code is possibly made more robust
	  (room/proximity-based) - its own task.
	3 Hydra (hydra.cpp, TypeID 63 in trview, confirmed in Andrea2.trc) - is actually NOT a
	  single enemy but 3 enemies (heads), each with its own life/hitpoints, appearing
	  together as one unit. Trigger-wise the Hydra reacts to markers per AI Pool Logic
	  (Pool A), but was still moved into the special category here because of the multi-body
	  structure.
	  ##  FUNDAMENTALLY SAFELY RANDOMIZABLE (as a group) - code analysis (InitialiseHydra,
	  hydra.cpp:18-36): all 3 items are placed at EXACTLY THE SAME position in the editor
	  (hence "all 3 on the same sector") - the visible lateral offset comes entirely from the
	  code, driven by the OCB field (trigger_flags), which here does NOT encode a pickup type
	  as usual but the chain position:
	    OCB 0 = center (no offset)
	    OCB 1 = Z += 384
	    OCB 2 = Z -= 384
	    (additionally always: X -= 256, y_rot fixed to 0x4000, start animation frame offset
	    by 30*OCB for movement variance between the 3 heads)
	  IMPORTANT for the randomizer: Hydra items must NEVER be caught by the blanket
	  "normalize OCB to 0" rule (see Item Pool IDs.txt) - that would stack all 3 heads
	  exactly on top of each other instead of the chain of 3. When moving the position, the
	  movement must be applied to all 3 items with an identical delta, OCB values left
	  unchanged, and enough room for the ~768-unit Z offset (half to one sector width) must
	  exist at the target.

	4 CHEF (chef.cpp, TypeID 87 in trview, confirmed in joby3.trc) - MUST be triggered/killed
	  with the crowbar. Confirmed by the user: if you kill him with weapons beforehand (his
	  health bar runs to 0), he still stays invulnerably active - a level softlock, since the
	  actual kill is never triggered.
	  ##  NOT RANDOMIZABLE - code analysis (ChefControl, chef.cpp:28-158): the whole state
	  machine checks item->hit_points NOWHERE. Weapon damage does apparently drain the health
	  display (the generic damage application runs normally), but the chef's own logic never
	  reacts to it - he hangs forever in the normal combat/patrol state. The only real death
	  runs via a LEVEL-SPECIFIC script cutscene (game\deltapak.cpp,
	  stealth3_start()/stealth3_end()) that sets item->hit_points/current_anim_state/
	  anim_number manually and directly instead of via the normal combat loop:
	    stealth3_start(): looks for CHEF/SAS/BLUE_GUARD/SWAT_PLUS/SWAT/TWOGUN near Lara
	      (< 1024/1024/256 units), hides the hit for the cutscene.
	    stealth3_end(): sets hit_points=0, current_anim_state=6/7, plays the crowbar finish
	      animation (anim_index+11 for CHEF) manually.
	  This function is hard-wired per level (the name "stealth3" points at a specific level
	  sequence, presumably joby3.trc itself). Move/swap CHEF to another spot/level without a
	  matching script function of its own and he is simply NEVER killable there - a
	  guaranteed softlock, not just a risk.
	  RECOMMENDATION: exclude CHEF completely from the randomizer pool (neither source nor
	  target).
