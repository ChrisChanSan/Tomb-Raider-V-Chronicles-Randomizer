# The tools, and which one answers which question

Fifty-four diagnostic tools sit in `Diagnose\`, forty-five of them with a
build script beside them. This page is their index: the way to find the
right one without already knowing it exists.

Every tool prints its own usage when started without arguments, and every
one carries a header comment saying why it was written. That header is the
authority; this page only points at it.

## Building

`Diagnose\<b*.bat>` - run it, it builds in place. Every script is relative to
its own folder, so a fresh clone builds them. They need Visual Studio with
the C++ workload; the path to `vcvars` is the one absolute thing in them.

`bmap.bat` and `btrg.bat` are no exception: every path in them is the
`%~dp0` form as well.

**The one prerequisite, said once here:** the `vcvars` line names a specific
Visual Studio installation. If yours sits elsewhere - a different edition, a
different major version - that single line in each script is what to change;
nothing else in them is machine-dependent. Two of the forty-seven `b*.bat` are
not tool scripts at all: `be.bat` builds the engine and `bshader.bat` compiles
the shaders. `bshader.bat` has no `vcvars` line but needs `fxc.exe` of the
Windows SDK (an optional component of the same workload, installed by
default), which it looks for in the two `Windows Kits\10\bin` folders under
`Program Files` and `Program Files (x86)`; it is needed only when a `.hlsl`
changes - a build of the published tree runs `be.bat` without it, because the
tracked `.inc` match their stamps.

Nine tools have no script and are built by hand from their header comment:
BoneCheck, CornerCheck, DinoCheck, FaceCheck, GeomTest, TR3FetchCheck,
TR3SoundCheck, TriggerCommands, WinCheck.

One header beside them is shared rather than a tool: `VisInput.h`, which RoomProbe
and TrgProbe both include for the visibility walk's inputs out of a `.TRC`.

`ModernTest` and `MenuTest` also read engine sources at run time, by their path from
their own EXE's folder (`Diagnose\`) and then from the working directory, so a start
from any folder gives the same counts.

CornerCheck, GeomTest and WinCheck were written in a scratch folder outside
the clone, and their build scripts stayed behind on purpose: those carried
absolute paths, and two of them were even named `bcc.bat` and `bwc.bat`,
which belong to CameraCheck and BalanceWriteCheck here. All three take the
same command line as CameraCheck's script - `Tr5Level.cpp` plus zlib, nothing
else - with their own name substituted.

| `RootProbe` | broot | the ROOT OFFSET of an animation - `frm[6..8]`, the three shorts the draw translates by after the item's own rotation - and what the 60 FPS in-between frame draws it as. Prints the animation table row with the fields `AnimCmd` does not read (where it continues, and at which FRAME), every animation command including type 1 `TranslateItem`, where each state change really goes, every key frame's offset, and then the WRAP REPLAY: three logic ticks either side of the wrap with the drawn root at thirty hertz, and the tween frames both as the engine drew them before the interpolation fix and as it draws them now.<br><br>It exists because a ladder carries its whole vertical travel inside those offsets and moves `item->pos` only once, at the wrap, so "the picture is continuous at thirty" is a statement about two numbers ADDING UP - and nothing else in the toolbox could read either of them. It also prints, for the tween frame the rule really reaches, the whole `INTERPLOG root lara` line that frame will produce in a `-log` run, in all three axes - because writing that line out by hand from the key table beside it is how a wrong x and z first got caught. `-grab <from> <to> [posStep]` does the same for a change from one animation to another, which is what the ladder grab is; where the change is the animation's own wrap, `posStep` defaults to that animation's `TranslateItem` rather than zero, so a bare `-grab 172 173` still shows the grab as the engine draws it. `-sweep [least]` walks every wrap and `jump_anim_num` change of Lara's whole animation table, prints the offset step, the leaving animation's own `TranslateItem` (or none) and the verdict - paid in full, paid in part, not at all - for every axis whose offset step is at least `least` units (default 8), and is the table the check itself reads. Its summary counts the invariant itself, beside the count that stop blending, instead of leaving the zero to be read off the per-row columns: how many rows draw OUTSIDE the segment from the frame's own offset to today's draw - further out or the other way - which must read 0, and does (0 of 433 in ANDREA1, 0 of 352 in JOBY5). That is the form of the invariant that can be violated; "blends where today's does not" is dead here, because a row only enters the sweep when an axis moves at least `least` units and today's half-blend then always lands off the frame's own offset. A tween row that rule K6 ACCEPTED says `(accepted frame - not drawn)` rather than `(rule does not fire)`: neither rule is asked on an accepted frame, so the two rows' differing numbers there are the arithmetic of a blend nobody performs. The `step=`/`kept=` line of the wrap and grab tables also prints `d_off=`, `today=` and `narrowed=` in words (`blends` or `stands down`) and `worst=`, the difference the two pictures grow to over a whole tween - which is the largest one, not the alpha-0.5 pair printed beside it; the verdict is printed in words so that it is never inferred from the absence of a marker on cases where neither rule fires. |

**Savegames**
| Tool | Script | What it answers |
|---|---|---|
| `SaveDiff` | bsd | two savegames compared **field by field, by name**. Prints `IDENTICAL` when the files match to the byte, otherwise one line per differing field with both values - so "played four seconds longer" (`Game.Timer`, the clock, Lara's position) is told apart at a glance from "the game ran differently" (`Level.Kills`, the ammunition counts, `Lara.air`). Written for the frame-rate proof: the draw path has its own RNG that the simulation never reads, so the same seed and the same inputs must arrive at the same state at 30 and at 60 frames a second, and a savegame is that state written down. The recipe is in `docs/Engine-Manual.md` under *Frame rate*.<br><br>Takes every offset from the engine's own `global/types.h` with `offsetof`, so it cannot go stale - and is therefore built **x86**, like `BalanceCheck` and `RoomProbe`: the structs are `#pragma pack(1)` but carry pointers, and a pointer is four bytes in the engine. What it cannot name is the savegame *stream* inside `SAVEGAME_INFO::buffer` - that is what `WriteSG` (`game/savegame.cpp`) packed in a variable-length, conditional order - so those are reported as differing byte runs with their offset. |
| `InterpTest` | bit | the ARITHMETIC of the 60 FPS interpolation, checked with no game, no level and no device. It **includes the engine's own `TOMB5 Code\TOMB5\game\interpolate_math.h`** rather than a copy of it, so it cannot drift from what the engine does: a change to the lerps or the snap thresholds is a change this test sees. 754 checks — the count the run itself prints, and the one at the end of this row — the short-angle lerp over a sweep of 16,256 angle pairs (that every one turns the SHORT way round and lands within a unit of halfway, with the 128 exact half-turns stepped over and asserted on their own), the position lerp over the whole coordinate range of a level, the snap thresholds against the engine's own speeds (a terminal fall interpolates, a sector-wide teleport does not), that a Manhattan sum is never smaller than the true distance, and the cadence: `framecount` and `DrawPhaseGame`'s alpha rule run for a simulated minute at both frame rates and through a hitch - 1800 logic ticks either way, exactly half the frames interpolated at sixty, none at thirty, every drawn step exactly half a tick.<br><br>It exists because a short angle blended the LONG way round is invisible almost all the time and looks like a rendering glitch when it is not: one enemy, facing roughly south, spinning backwards for half a tick on every second frame. That has to be proven at the wrap, and a play test will not put a body on the wrap when you want it to. `counters` is a simulated wall-clock second at both rates with the engine's own tween-frame rule, asserting that a guarded counter steps thirty times in BOTH modes (not sixty), that the nine-step screen fade spans the same nine ticks - 2n-1 presents at sixty, because it begins and ends on a live frame - and that at `fps_mode 0` not one frame is ever an in-between frame. It also states the rule's one honest limit: a frame that ran long carries TWO logic ticks and can only step a counter once, so a counter falls one behind per doubled frame and does not catch up - which is what the thirty hertz engine does too. `pose_factor` and `pose_time` transcribe the four hard-wired blend branches of `game\draw.cpp` as the REFERENCE and compare them against the header's one float factor over 441 matrix element pairs for every `(frac, rate)` the retail levels can produce - 336,471 animation frames' worth, then every pair up to rate 32 - with a **maximum difference of 0 units on both the float and the integer stack**, which is what makes `fps_mode 0` still byte-identical; and the pose is walked over a whole animation at sixty hertz and printed as a table (rate 4 comes out as even eighths, rate 2 as even quarters, rate 1 - which never interpolated at all in vanilla - as exact halves, rate 5 as vanilla's own uneven steps with a midpoint between each pair), asserting that it never walks backwards, never leaves its key frame pair, is vanilla's own value on every tick frame, follows an animation's shortened last interval, and is refused by each of the six K6 cases. `refresh` is for the frame rate bound to the display: it models the engine's own loop - draw, flip at the panel's vblank, read the clock AFTER the flip, hand the whole ticks to `ControlPhase` - with the vblanks on their own grid at their own phase, so the two clocks are as independent as a 144 Hz panel and a 1/60 s counter really are. Ten simulated seconds at 60, 120 and 144 Hz each run **300 logic steps** against 600, 1200 and 1440 frames; the blend factor is **never clamped** (a clamp means a frame asked for a state the logic has not computed, and the picture stands still for it); no frame draws what the one before it drew; exactly one frame per logic tick carries the per-frame counters, which at these rates cannot be `alpha < 1`; and what is drawn tracks the wall clock with a spread under 1e-7 ticks, which is a float's precision and not drift. A 200 ms hitch is caught up rather than dropped, less the two ticks vanilla's own `if (nframes > 10)` cap discards. `particles` is a falling particle under gravity, simulated tick by tick and drawn beside an ITEM whose previous state really is remembered, at sixty hertz and at 144 - the two must agree **to the unit on every single frame**, and the particle must never be drawn past the state the game holds, never before the state it came from and never a step backwards. The identity is also swept over every step a TR5 particle can carry, in both signs, against the obvious rearrangement `cur - step * (1 - alpha)`, which disagrees on 16,384 of the 40,965 pairs - that is the rounding trap the engine's form avoids, and it is printed rather than described. `camera_aim` and `title_cadence` are both faults a play test found written down as arithmetic. `camera_aim` runs the OLD target rule beside the new one over a swept first person camera whose target sits at the engine's own `0x5100`: the old rule cuts on a three degree head turn - under it `INTERPLOG` reads `camcut=10..17` a second with Lara standing still - and the new one cuts on no turn up to twenty degrees a tick in either axis with the eye moving as well (over 500 cases), still cuts at sixty, ninety and a hundred and eighty degrees, leaves a chase camera alone, still catches a target jumping two sectors, and hands a near target back as its own offset to the unit. `title_cadence` runs the title menu's own two-ticks-a-present accumulator from both parities: at two ticks `framecount += 2; while (> 0) tick, -= 2` RETURNS TO WHERE IT STARTED, so a title entered on -1 stayed on -1 and the old rule made every one of its frames an in-between frame - which stopped the screen fade, left `DoFade` at 1 and put a black quad over the menu for ever. The new rule makes none on either parity and the logic tick count is unchanged. `pose_wrap` answers a dive roll's one-frame glitch - a leg fully extended the wrong way - against the arithmetic the engine really runs: the blend treats the two poses as MATRICES and never as angles, so the packed 1000-to-20 case is put through that very blend on all three axes and in both directions and comes back at 1022, never at 510. What DOES go wrong is the shrink - an element-wise lerp of two rotations keeps cos(D/2) of the bone's frame, and at half a turn it keeps nothing - so the group also asserts `InterpPoseFar`, the rule that refuses a RATE 1 pair (the only kind vanilla never blends at all) whose two poses turn more than ninety degrees at any node: it fires on a half turn, leaves a fourteen degree turn alone, never fires on a pose against itself, and its limit sits where it says it does. `camera_shell` closes a seam on `INTERP_CAM_FAR_TARGET`: the branch is chosen once for the PAIR and both sides take the same scale, so a target walking out through the shell one unit at a time (500 steps) and a target jittering on it for thirty ticks read no cut at all. `level_camera` walks the two flags of a level camera sequence (`bUseSpotCam`, `bTrackCamInit`) through snapshot, tick and frames the way `ControlPhase` sets them, at 165 frames to 30 ticks a second, against `InterpLevelCamHolds`, `InterpSpotCut` and `InterpEyeRuleRuns`: a sequence that tracks Lara cuts on its entry tick and its exit tick only, every frame of its 119 continuing ticks is blended with the drawn-eye rule off (`bUseSpotCam` alone cut all 120 of them), a call of two ticks adds no cut, nothing counts outside a sequence, and a flyby that does not track counts frame for frame as with `bUseSpotCam` alone. `portal walk` is the arithmetic of the two tests that lose a room on a tween frame, run on ANDREA1's own portal records; `reach` is the two rectangles of the portal walk on JOBY2's - room 124's window `0,0..535,719`, the portal 124 -> 99 projecting to `542,116..754,389`, and the classic clamp leaving `535,116..535,389`, which has no width at all and is the black hole a play test found - plus the invariant this rests on (the classic rectangle lies inside the reach's, over 2,000 random pairs) and the ring of rooms that says what the reach's seen-mark is for. `walk_capacity` is the arithmetic that says no loadable level can fill the walk's two arrays: the queue ring's size is a power of two and `& (size - 1)` agrees with `% size` over 5,000 consecutive writes, and the engine's own queue loop - interlock and capacity guard included - is run over the worst graph there is, 256 rooms each with a portal to every other, where the queue never gets deeper than the room count and `draw_rooms` takes one entry per room. The same level against a ring of 128, which is what the engine had before, DOES trip the guard, so the passing case is not a tautology. `ring_cadence` and `title_shadow` are for the inventory ring and the title menu at the frame rate. `ring_cadence` runs the ring's own accumulator - `InterpRingStep`, `InterpRingAlpha` and `InterpRingSlide`, which live in the engine's header beside everything else here - at both rates: 600 frames at sixty run 300 steps with the clock agreeing with the parity shortcut on every one, ten seconds at 165 Hz run 300 steps against 1650 frames with the factor never clamped and the drawn instant never walking backwards, and a 333 ms hitch does NOT leave the ring stepping on every frame afterwards. It also holds the design question the group settled: the ring STEPS and then draws, where the game DRAWS and then ticks, so an arrangement where the in-between frame carries the blend is run here beside the one the engine implements, on the same simulated spin: **that arrangement walks backwards on 200 of 400 frames and the engine's on none**, every drawn step exactly half of the ring's own 1022. The same simulated hold is run through the title's loop at two ticks a present and at one, with and without the shadow: one tap is acted on once, twice, and once again. `root_flip` is for the underwater roll's own one-frame glitch: the engine's `InterpRootFlip` turns the previous root offset by the same 180 degrees a `turn180_effect` animation change flips y_rot by, measured against ANDREA1's own animations 203 and 205 (`RootProbe -grab`) rather than assumed - the drawn offset across the flip stays within 0.6 units of the true world point where the untouched blend was off by up to 160. `root_narrow`, 25 checks, holds `InterpRootNarrow`: it keeps the ladder's whole step (equal to `InterpRootLerp(prev, cur, t)` for every `t` in 1/256 steps), keeps nothing of the crawl-to-crouch step (result `== cur` for every `t`), a partial case, same-sign and zero steps, each axis on its own, the flip run before the narrowing, and `LONG_MIN`/`LONG_MAX` steps without overflow. `pose_back` holds `InterpPoseBack`, the rule for a frame that stepped DOWN - the Ledge hang's lowering plays the pull-up backwards three frames a tick: over rates 1, 2, 4 and 5 and every step up to three it is accepted exactly when the two frames lie within one key interval, starts on the previous tick's pose at t = 0, ends on the current tick's at t = 1, is exactly their midpoint at a half and never walks upwards; | `ModernTest` | bmt | the ARITHMETIC of the modern control - movement, the camera and the water - checked with no game, no level and no pad. It **compiles the engine's own `TOMB5 Code\TOMB5\game\modern_move.cpp` and `game\modern_camera.cpp`** beside itself rather than a copy of either - both files deliberately include no engine header at all, which is why they link here with a compiler and nothing else - so a change to either decision tree is a change this test sees. Prints `15508 checks, 0 failed` and returns 0. picture proves the arithmetic and the animation; which vertices get it is the
engine's business. The scroll and wind are NOT in
that class - they are marked in the `.TRG` itself, so what the tool draws there
is what the engine draws.

`bshader` is not a tool but a build step of its own: it runs `fxc` from the
Windows SDK over `specific\hd\hd_shader\*.hlsl` and writes the bytecode next to
it as `.inc` byte arrays. The engine's project has **no** shader compile step.
Both the `.hlsl` and the generated `.inc` are checked in — GPLv3 wants the
source that produced the bytecode to sit beside it.

**`be.bat` checks that for you.** Every `.inc` carries
the MD5 of the `.hlsl` it came from on its last line (`bshader.bat`, `:stamp`),
and the five whose shader includes another `.hlsl` (glow and water look
include `hd_room.hlsl`, the shadow caster `hd_model.hlsl`) carry that file's
MD5 on the line before (`:incstamp`). `be.bat` compares all 36 `.inc` before
it builds; where they differ it prints
`be: regenerating shaders - ... out of step with the HLSL`, runs `bshader.bat`
itself and only then builds, and it refuses to build at all if that fails. A
**content** stamp and not a file date, because a fresh clone gives every file
the same date and a date guard would then either cry wolf or say nothing at
all.

**`be.bat` also compiles the whole engine on every run** (`msbuild
/t:Rebuild`, about half a minute), never only what `msbuild` takes for
changed. `msbuild` goes by file dates: a source file put back with a date
older than its object file - a copy that keeps the date, an archive unpacked
over the tree - is passed over although its content is new, and the link
joins object files of two states of one header. Such a binary compiles, links
and can die at once. The full build leaves no such mix possible, and it gives
every binary its own build time (`winmain.cpp` writes it as the first line of
a `-log` run).

**And a content stamp has its own trap.** An MD5 is taken over bytes, and
line endings are bytes: with
git's Windows default the `.hlsl` came out of a fresh clone with carriage
returns the stamped file never had, so the guard fired on shaders that were
perfectly in step, rebuilt them, and left two tracked files modified in a
clone nobody had touched. Worse, the two pairs disagreed with each other -
one had been stamped over LF, the other over CRLF - so on any machine one of
them was lying. The fix is one rule in `.gitattributes`, `eol=lf` for
`**/hd_shader/*.hlsl` and `*.inc`, so every machine hashes the same bytes;
the four `.inc` were regenerated over LF sources and proved to differ from
their predecessors in the stamp line alone. Nothing in the scripts changed.
If you edit a shader, keep its file LF. It exists because a shader source
once changed without `bshader` being run, and the build shipped with its
source and its picture disagreeing - nothing in the tree could say so, and it
took a play test to find. Running
`bshader.bat` by hand still works and is still the right thing to do while
iterating on a shader; the guard is the net underneath.

## The other half: the engine tells you things too

The engine writes nothing unless it is started with `-log`. `Log.bat` in the
release package does exactly that, which is why it is in there. The seams
below are permanent - they are not debug leftovers to be tidied away, they
are how a player's crash report becomes usable.

| Symptom | Seam | What it prints |
|---|---|---|
| the wrong sound plays | `SFXLOG` | which sample really played, and which anim command asked for it |
| an enemy is invisible | `SLOTLOG`, `SKIPLOG`, `MESHLOG`, `CLIPLOG` | the four separate reasons: no free AI slot, control skipped it, no mesh, clipped away |
| ...and if it is the clipping | `CLIPDETAIL` | the actual window and the camera it was measured against |
| an item is in the wrong place, or vanishes | `ITEMLOG` | slot, room, OCB, flags per item at load |
| ...and something moves it later | `ITEMWATCH` | who wrote which room number, and when |
| an enemy carries an item off, or does not | `CARRYLOG` | per pickup in a carrier's reach at level start: carrier, item, OCB, offset, carried or skipped wall grab |
| the outfit looks wrong, a limb is misplaced | `SKINLOG` | the skin's bone stack |
| the first-person view sits wrong | `FPHEAD`, `ALTERFOV` | the head bone per frame, and the field of view |
| an HD object or Lara is wrong, or classic when it should not be | `HDLOG` | per level: which slot got which model and why it was refused; Lara's outfit, her parts and the reason for a classic one. Per level's first HD frame: `itemcheck` and `lightcheck` for the objects, `laracheck` and `braidcheck` for Lara |
| one room's HD art shows on another room's wall, or a wall is seen from behind | `HDLOG` | per level: one `overlap` line per pair ending in `faces=` and `bound=` (the intruder's classic faces its art belongs to, and the triangles they claim), the level line ending in `holder=inside cull=opaque faces= bound= unbound= band_unclaimed=` (the last the unclaimed art near a holder's wall, drawn whole on every frame), and `HDLOG cull level=... ranges opaque= two_sided=`; once a second the `clip` line ending in `pairs= whole= scissored=` - the pieces of intruding art the frame asked about, drew whole and cut - and `reach_rooms= reach_pieces= reach_whole= reach_hidden=`, the rooms the reach lists with no window and their pieces, drawn whole outside the box one sector smaller or left out inside it, with one `reachart` line per such room and holder (`reach=`, `holder=` the holder's group - the room of that number until a flipmap swaps it with its pair, `listed=`, `pieces=`, `tris=`, `answer=whole\|hidden`, `band_tris=`), written with the `clip` line and on the frame of a window event's ROOMLIST dump. The level line goes on with `air_ms= air_tris= air_groups= air_pairs= air_boxed= air= covered=` (`covered` the classic faces inside a larger face of a room their room stands in, whose art is drawn pushed back) and one `unlinked level= group= host= tris=` line per pair follows, and with `hd_air` 1 or 2 one `hull level= group= air_tris= host_art= hull= behind=` line per group with such art (`behind` the triangles drawn pushed back) - art standing in the air of a room its own room has no portal, door or vertical link with, not even through a flipmap twin; the `air_boxed` part of it, the art an intrusion entry's box holds, is drawn only inside its own room's window unless the classic path draws a face of that room that claims it, and `air=` is the `hd_air` setting the level took (0: no air asked, every `air_` field 0) - and the `clip` line ends with `unlinked_pieces= unlinked_drawn= unlinked_hidden=`, the frame's pieces of such art, those drawn (inside their window or whole on a claimed face) and those left out with an empty one. `TrgProbe -roomspace` prints the same pair lines, the same `band_unclaimed=` and the same `unlinked` lines offline; `RoomProbe -unlinked 0|1|2` draws such art as without the air rule (0), as the engine does (1, the default) or as the engine does but for a group whose window is empty, whose pieces keep the smaller box's answer (2) - the other answer for an empty window, held against the engine's at the same place |
| which rooms the visibility path drew, and why (`hd_vis` 1) | `HDLOG`, `VISLOG` | per level once, at the first frame that asks: `HDLOG level= vis=1 rooms= art_rooms= walls= bare= void= guests= guest_tris= wide= ms= twin= wide_bare= edge= statics_held= statics_ms= enclosed=` - the rooms whose walls were asked, their classic wall faces, the bare ones (the openings), those with no linked room behind, the guests and their triangles, the portals with a wider opening, the tables' build, the openings that named a flipmap pair's other room (named by its main room), the bare share that widens a portal and the window's edge, the static meshes left to the art that lies on them and what asking them cost, and the rooms standing inside a linked room's art. Once a second and whenever the eye's room changes `VISLOG frame= eye_room= rooms= walk= guest= opening= wide= dequeues= list= edge= near=` - the listed rooms, how many each source queued first, the walk's dequeues, and every listed room with the letter of its source (`w` a portal, `g` a guest, `o` an opening, `p` a wide portal, `e` a portal at the window's edge, `n` a portal the eye stands at), the rooms the window's edge queued, and at the line's end `near=` the rooms a portal the eye stands at queued. `RoomProbe -vis 1 -walk ... -walkfinal` prints the same per room offline |
| the list of rooms a view was drawn with, at the moment a picture was taken | `ROOMLIST` | the whole list with each room's `window=` and `reach=`, written every five seconds and on the first frame after every `WM_INACTIVE` and `WM_ACTIVE` - a tool that captures the screen takes the focus away and gives it back - its header ending in `why=timer\|inactive\|active`; between them one line per change of the list, at most 20 a second. `RoomProbe -walkdump` walks every whole-list dump of a log again |

| in HD a marble floor shows no reflection, or a washroom mirror shows no Lara and no doors | `HDLOG` | per level: the motion line ending in `clear_pages= clear_parts=` (the part-way clear floor pages and the parts on them - RICH2, RICHCUT2 and TITLE have some) and `mirrors=`, one `mirrorwall level= room= axis= plane= side= pane= behind= mirrored= box=` line per mirror the build found; the level's first frame line ending in `clear_calls=`; and once a second while a mirror draws anything `HDLOG mirror items= plane= room= axis= lara= hd= win=` - the items it reflected, the glass, whether Lara was in it, how many items went through the HD models, and `win=` the copy's rectangle on the screen as left, top, right, bottom (right and bottom exclusive), which a reflection drawn the classic way is cut to. | the poison sway is missing or faint at 60 | `POISONLOG` | written only while Lara is poisoned. A `view` line per view build: `call=` (the running count), `tick=` (`GlobalCounter`), `tween=` (the tween latch), `rebuild=` and `who=` (`rebuild` for the interpolator's own two per frame, `tick` for the tick's camera, `other` for the pickup icon, the gun's aim view and the rest), the amplitude `poisoned=` after the ramp and its goal `dpoisoned=`, and `scale=`, the three factors applied (16384 is unscaled). A `frame` line per drawn frame, right after the frame's interpolation is set up: `frame=`, `tick=`, `tween=`, `alpha=` and `base=`, the three column lengths of the matrix stack's base every draw of the frame starts from, times 10000 (10000 is unscaled), and `poisoned=`. | at *Frame rate 60* a cut scene steps, jumps, or an actor or Lara flicks for a frame | `CUTLOG` | `open` per cut scene (`cutseq=`, `frames=`, `actors=`, `nodes=`, `fps_mode=`); a `cut` line per game step drawn wholly or partly live (`why=camera` with the eye and target steps, `actor` with the root step, `halfturn` with the node, `open`, `skip`, `close`); `close` with `frames=`, `ticks=`, `blended=`, `live=`, `cuts=`, `actor_cuts=`, `halfturns=`, `hair=` (the braid's steps - one per game step), `eye_rooms=` and `hair_lag=`. `CutseqProbe -cutlog <n>` prints what the file says the same run must write |
