# The tools, and which one answers which question

Written 2026-08-30 from the folder itself, four tools added 2026-09-03, two
more 2026-09-05, `SaveDiff` and `InterpTest` on 2026-09-07, `FontProbe` on
2026-09-09. Forty-three diagnostic tools sit in `Diagnose\`, thirty-four of
them with a build script beside them, and until now there was no index at
all - so the way to find the right one was to already know it existed.

Every tool prints its own usage when started without arguments, and every
one carries a header comment saying why it was written. That header is the
authority; this page only points at it.

## Building

`Diagnose\<b*.bat>` - run it, it builds in place. Every script is relative to
its own folder, so a fresh clone builds them. They need Visual Studio with
the C++ workload; the path to `vcvars` is the one absolute thing in them.

Nine tools have no script and are built by hand from their header comment:
BoneCheck, CornerCheck, DinoCheck, FaceCheck, GeomTest, TR3FetchCheck,
TR3SoundCheck, TriggerCommands, WinCheck.

CornerCheck, GeomTest and WinCheck were written in a scratch folder outside
the clone, and their build scripts stayed behind on purpose: those carried
absolute paths, and two of them were even named `bcc.bat` and `bwc.bat`,
which belong to CameraCheck and BalanceWriteCheck here. All three take the
same command line as CameraCheck's script - `Tr5Level.cpp` plus zlib, nothing
else - with their own name substituted.

**Savegames (#148)**
| Tool | Script | What it answers |
|---|---|---|
| `SaveDiff` | bsd | two savegames compared **field by field, by name**. Prints `IDENTICAL` when the files match to the byte, otherwise one line per differing field with both values - so "played four seconds longer" (`Game.Timer`, the clock, Lara's position) is told apart at a glance from "the game ran differently" (`Level.Kills`, the ammunition counts, `Lara.air`). Written for the frame-rate proof: the draw path has its own RNG that the simulation never reads, so the same seed and the same inputs must arrive at the same state at 30 and at 60 frames a second, and a savegame is that state written down. The recipe is in `docs/Engine-Manual.md` under *Frame rate*.<br><br>Takes every offset from the engine's own `global/types.h` with `offsetof`, so it cannot go stale - and is therefore built **x86**, like `BalanceCheck` and `RoomProbe`: the structs are `#pragma pack(1)` but carry pointers, and a pointer is four bytes in the engine. What it cannot name is the savegame *stream* inside `SAVEGAME_INFO::buffer` - that is what `WriteSG` (`game/savegame.cpp`) packed in a variable-length, conditional order - so those are reported as differing byte runs with their offset. |
| `InterpTest` | bit | the ARITHMETIC of the 60 FPS interpolation (#148, orders 2, 3, 4, 5 and 6; #154), checked with no game, no level and no device. It **includes the engine's own `TOMB5 Code\TOMB5\game\interpolate_math.h`** rather than a copy of it, so it cannot drift from what the engine does: a change to the lerps or the snap thresholds is a change this test sees. 361 checks — the count the run itself prints, and the one at the end of this row — the short-angle lerp over a sweep of 16,256 angle pairs (that every one turns the SHORT way round and lands within a unit of halfway, with the 128 exact half-turns stepped over and asserted on their own), the position lerp over the whole coordinate range of a level, the snap thresholds against the engine's own speeds (a terminal fall interpolates, a sector-wide teleport does not), that a Manhattan sum is never smaller than the true distance, and the cadence: `framecount` and `DrawPhaseGame`'s alpha rule run for a simulated minute at both frame rates and through a hitch - 1800 logic ticks either way, exactly half the frames interpolated at sixty, none at thirty, every drawn step exactly half a tick.<br><br>It exists because a short angle blended the LONG way round is invisible almost all the time and looks like a rendering glitch when it is not: one enemy, facing roughly south, spinning backwards for half a tick on every second frame. That has to be proven at the wrap, and a play test will not put a body on the wrap when you want it to. Order 3 added a `counters` section: a simulated wall-clock second at both rates with the engine's own tween-frame rule, asserting that a guarded counter steps thirty times in BOTH modes (not sixty), that the nine-step screen fade spans the same nine ticks - 2n-1 presents at sixty, because it begins and ends on a live frame - and that at `fps_mode 0` not one frame is ever an in-between frame. It also states the rule's one honest limit: a frame that ran long carries TWO logic ticks and can only step a counter once, so a counter falls one behind per doubled frame and does not catch up - which is what the thirty hertz engine does too. Order 4 added `pose_factor` and `pose_time`: the four hard-wired blend branches of `game\draw.cpp` transcribed as the REFERENCE and compared against the header's one float factor over 441 matrix element pairs for every `(frac, rate)` the retail levels can produce - 336,471 animation frames' worth, then every pair up to rate 32 - with a **maximum difference of 0 units on both the float and the integer stack**, which is what makes `fps_mode 0` still byte-identical; and the pose walked over a whole animation at sixty hertz, printed as a table (rate 4 comes out as even eighths, rate 2 as even quarters, rate 1 - which never interpolated at all in vanilla - as exact halves, rate 5 as vanilla's own uneven steps with a midpoint between each pair), asserting that it never walks backwards, never leaves its key frame pair, is vanilla's own value on every tick frame, follows an animation's shortened last interval, and is refused by each of the six K6 cases. Order 6 added `refresh`, for the frame rate bound to the display: it models the engine's own loop - draw, flip at the panel's vblank, read the clock AFTER the flip, hand the whole ticks to `ControlPhase` - with the vblanks on their own grid at their own phase, so the two clocks are as independent as a 144 Hz panel and a 1/60 s counter really are. Ten simulated seconds at 60, 120 and 144 Hz each run **300 logic steps** against 600, 1200 and 1440 frames; the blend factor is **never clamped** (a clamp means a frame asked for a state the logic has not computed, and the picture stands still for it); no frame draws what the one before it drew; exactly one frame per logic tick carries the per-frame counters, which at these rates can no longer be `alpha < 1`; and what is drawn tracks the wall clock with a spread under 1e-7 ticks, which is a float's precision and not drift. A 200 ms hitch is caught up rather than dropped, less the two ticks vanilla's own `if (nframes > 10)` cap discards. Order 5 added `particles`: a falling particle under gravity, simulated tick by tick and drawn beside an ITEM whose previous state really is remembered, at sixty hertz and at 144 - the two must agree **to the unit on every single frame**, and the particle must never be drawn past the state the game holds, never before the state it came from and never a step backwards. The identity is also swept over every step a TR5 particle can carry, in both signs, against the obvious rearrangement `cur - step * (1 - alpha)`, which disagrees on 16,384 of the 40,965 pairs - that is the rounding trap the engine's form avoids, and it is printed rather than described. Fix round R added `camera_aim` and `title_cadence`, and both are a fault the play test found written down as arithmetic. `camera_aim` runs the OLD target rule beside the new one over a swept first person camera whose target sits at the engine's own `0x5100`: the old rule cuts on a three degree head turn - which is why `INTERPLOG` read `camcut=10..17` a second with Lara standing still - and the new one cuts on no turn up to twenty degrees a tick in either axis with the eye moving as well (over 500 cases), still cuts at sixty, ninety and a hundred and eighty degrees, leaves a chase camera alone, still catches a target jumping two sectors, and hands a near target back as its own offset to the unit. `title_cadence` runs the title menu's own two-ticks-a-present accumulator from both parities: at two ticks `framecount += 2; while (> 0) tick, -= 2` RETURNS TO WHERE IT STARTED, so a title entered on -1 stayed on -1 and the old rule made every one of its frames an in-between frame - which stopped the screen fade, left `DoFade` at 1 and put a black quad over the menu for ever. The new rule makes none on either parity and the logic tick count is unchanged. Fix round S added `pose_wrap` and `camera_shell`. `pose_wrap` answers the play test's dive roll - one tween frame with a leg fully extended the wrong way - against the arithmetic the engine really runs: order 4 blends the two poses as MATRICES and never as angles, so the packed 1000-to-20 case is put through that very blend on all three axes and in both directions and comes back at 1022, never at 510. What DOES go wrong is the shrink - an element-wise lerp of two rotations keeps cos(D/2) of the bone's frame, and at half a turn it keeps nothing - so the section also asserts `InterpPoseFar`, the rule that refuses a RATE 1 pair (the only kind vanilla never blends at all) whose two poses turn more than ninety degrees at any node: it fires on a half turn, leaves a fourteen degree turn alone, never fires on a pose against itself, and its limit sits where it says it does. `camera_shell` closes the seam fix round R left on `INTERP_CAM_FAR_TARGET`: the branch is chosen once for the PAIR now and both sides take the same scale, so a target walking out through the shell one unit at a time (500 steps) and a target jittering on it for thirty ticks read no cut at all, while round R's own answers stand. `portal walk` (#123, fix round T2) is the arithmetic of the two tests that lose a room on a tween frame, run on ANDREA1's own portal records; **`reach` (#123, fix round T4)** is the two rectangles of the portal walk on JOBY2's - room 124's window `0,0..535,719`, the portal 124 -> 99 projecting to `542,116..754,389`, and the classic clamp leaving `535,116..535,389`, which has no width at all and is the black hole of the play test - plus the invariant the round rests on (the classic rectangle lies inside the reach's, over 2,000 random pairs) and the ring of rooms that says what the reach's seen-mark is for. Fix round T5 added `walk_capacity`, the arithmetic that says no loadable level can fill the walk's two arrays: the queue ring's size is a power of two and `& (size - 1)` agrees with `% size` over 5,000 consecutive writes, and the engine's own queue loop - interlock and capacity guard included - is run over the worst graph there is, 256 rooms each with a portal to every other, where the queue never gets deeper than the room count and `draw_rooms` takes one entry per room. The same level against a ring of 128, which is what the engine had before T5, DOES trip the guard, so the passing case is not a tautology. Round 154 added `ring_cadence` and `title_shadow`, for the inventory ring and the title menu at the frame rate. `ring_cadence` runs the ring's own accumulator - `InterpRingStep`, `InterpRingAlpha` and `InterpRingSlide`, which live in the engine's header beside everything else here - at both rates: 600 frames at sixty run 300 steps with the clock agreeing with the parity shortcut on every one, ten seconds at the user's own 165 Hz run 300 steps against 1650 frames with the factor never clamped and the drawn instant never walking backwards, and a 333 ms hitch does NOT leave the ring stepping on every frame afterwards. Then the measurement that settled the round's one design question. The ring STEPS and then draws, where the game DRAWS and then ticks, so the arrangement the round was briefed with - the in-between frame carrying the blend - is run here beside the one the engine implements, on the same simulated spin: **the briefed arrangement walks backwards on 200 of 400 frames and the engine's on none**, every drawn step exactly half of the ring's own 1022. The spin is also walked over the 65536 wrap four times with not one long-way frame, and the slide is walked through three whole turns of the ring with the reset - `objlistmovement` back to 0 and `curobjinlist` moved on - never blended halfway back. The same walk asserts the PAIR, which is a bug this round had and this test now holds shut: the slot the row is laid out from and the offset it is drawn with must come from ONE generation, because the reset moves both in the same breath and a frame that took the new slot with the old offset put the whole row seven eighths of a slot to the side. `InterpRingSlot` is that rule, and a slot left over from a list that has since been rebuilt falls back to the live one. `title_shadow` is order 1b's finding as arithmetic, and it corrects the rule this round was briefed with: the debounce is TWO statements with the frame's own read between them (`specific\input.cpp:821` and `:881`), so `dbinput` is the rising edge against the PREVIOUS FRAME'S INPUT and its own incoming value is thrown away - zeroing it would not turn a held key into a press. What the restore really buys is the hitch: `SetDebounce` is cleared inside the first tick of a `ControlPhase` call, so a call that runs three ticks writes `dbinput` on one of them, and an unrestored zero swallows the edge for the other two (asserted as 3 reads against 1). The same simulated hold is run through the title's loop at two ticks a present and at one, with and without the shadow: one tap is acted on once, twice, and once again. Prints `361 checks, 0 failed` and returns 0. |

**The HD art of the Remaster (#123)**

These read the user's own *Tomb Raider IV-VI Remastered* installation where it
lies. Nothing of it is copied into this tree, and none of them touch
`tomb456.exe` or `tomb5.dll`.

| Tool | Script | What it answers |
|---|---|---|
| `TrgProbe` | btrg | what is in a `LEVELn.TRG`: groups, parts, passes, pages, vertices, indices, and how many draw ranges a level would cost. `-mat [n]` lists the distinct `(material, param)` tuples; `-matparts <n>` takes ONE material apart part by part — the pass the file sorts it into, the y span and how many distinct heights are in it, the world box and how many floor squares it covers, which way the normals face, `sway`, the pages, the two baked colours, the UV span, and whether any of its vertices is shared with a part of another material — and with `-classic` it puts the classic room's own flags and horizontal planes beside it, so "does this part sit in the water plane" is a subtraction. |

| `DdsProbe` | bdp | decodes one BC7 `.DDS` with the engine's own decoder and writes a `.PNG`, so what the tool shows is what the game will show. |
| `FontProbe` | bfont | **where every classic glyph lives in the remaster's font atlas, and what a line of text looks like drawn from there** (#123, fix round Q). It compiles the engine's own matcher (`specific\hd\hd_fontmatch.cpp`), the engine's own BC7 decoder and the engine's own glyph and accent tables (`game\chardef.inc`, `game\accent.inc`), so a letter it finds is the letter the game finds. `-pages <file.trc> ...` prints the md5 of each file's font page - the question behind it being whether the match has to run per level or once (it is once: all sixteen shipped files carry the same page). `-match <level.trc> <TEXdir> [<png dir>]` matches the 106 rectangles against `FONT0_OG.DDS` and `FONT1_OG.DDS`, prints the table (glyph, score, position) and writes `font0_pairs.png` / `font1_pairs.png`, all 106 glyphs as "classic | HD" side by side with the misses marked red - which is how one sees at a glance that `FONT1` is Cyrillic and rightly refused. `-atlas <level.trc> <TEXdir>` measures the three things the draw seam rests on: whether the big picture really is the small one times eight (it is not - 12.6 % of the texels differ), how far the ink reaches past the eightfold rectangle, and whether the ink is white with an alpha channel or pre-coloured; it also prints what margin each glyph really gets. `-sample <level.trc> <TEXdir> <out.png> <text> [margin]` draws one line classic and the same line HD through the very arithmetic `DrawChar` uses, one over the other in a single picture, and says how far the two disagree - `%NN` in the text is accent row NN of `accent.inc`, so `"M%4rkte M%1hle"` is a word with two umlauts. `<TEXdir>` is `<remaster>\5\TEX`; nothing is written there and nothing is copied. |
| `RoomProbe` | broom | **draws one room** with the engine's own HD renderer into a `.PNG`, from a camera you give it, without starting the game. Also prints the depth proof (classic `sz` against the projection matrix over 50 distances), reads back what the device really compares depth with, checks the state bracket over 58 device states, measures the page cache in both texture pools, and with `-matrixcheck` prints the world-matrix proof: the engine's own three transform lines against the matrix that goes to the card, over up to 128 of the room's vertices, worst difference in **pixels**. Built **x86**, unlike its neighbours: the number it exists to measure is the peak commit of a 32-bit process.<br><br>The stage S2b switches make up the engine state the tool has no engine for and hand it to the very structures `hd_level.cpp` fills in the game: `-light <x y z r g b falloff>` a torch (room-local, repeat for up to 8), `-bulb <x y z rad den [r g b]>` a fog bulb (room-local; the tool transforms it into view space as `aBuildFogBulbList` does, up to 6), `-fog <start end r g b>` the distance fog (only `start` reaches the picture - TR5's fog has no end and no colour, and the tool says so rather than pretending), `-underwater`, `-shimmer`, `-effect <0..21>` the WaterTable row, `-wibble <n>` the engine's own counter - two runs with two values are two moments in the water. `-paritycheck` runs the classic formula and the shader formula over up to 200 of the room's own vertices on the processor and prints the worst difference per channel; the budget is 2 of 255.<br><br>The stage S5 switches say what MOVES: `-time <seconds>` is the game clock the UV scroll and the wind ride on, and it also sets the wibble counter to the value the engine would have at that second, so two `-time` runs are two moments of the WHOLE picture and not of half of it; `-water` declares the drawn room a water surface (the same whole-room override `-shimmer` uses); `-nomotion` is the engine's `hd_motion = 0`. `-animtex` prints, room by room, what the `.TRG` itself says moves there: scrolling draw calls with their speed in page units per second (material 1), vertices carrying a wind weight and the largest of them (`TrgVertex::sway`), and the flipbook parts (material 13) that are counted and NOT drawn - so the size of that gap is a number per level.<br><br>The stage S6 switches are the small card, which no machine here has: `-budget <MiB>` forces a texture budget (over it the largest pages give up their largest mip level, biggest first, never a whole page), `-format rgba|dxt5` holds the pages compressed instead of lossless and `-psnr` says in decibels what that costs, `-caps maxtex <n>` and `-caps noidx32` bend the caps the renderer read from the device so the fallbacks can be seen at all, `-vramhog` fills the card with 64 MiB blocks until it refuses so the out-of-video-memory path runs, and `-seq <A,B,C>` builds those levels one after the other printing commit and free texture memory between each - the proof that a level change never holds two levels at once.<br><br>**`-hdm` applies the `.hdm` sidecar** beside the classic `.TRC` that `-roombox` points at, the way `hd_level.cpp`'s `BuildRoomCuts` does and with the engine's own reader compiled in (#123, fix round Z): every opening the randomizer cut is taken out of EVERY group's art at build time and what each box caught is printed per room, and a room the sidecar names WHOLE is not drawn at all - which is the hole the engine leaves for the classic path to fill, and the thing the round had to photograph. Needs `-roombox`, because that folder is where the sidecar lives. Without the switch the very same files draw with every room whole and the doorway still shut, which is the before picture out of the same build.<br><br>**`-watersurvey <classic folder>` is the water in one run** (#123, fix rounds H and N): per reflecting room, how many classic faces sit in the plane the engine draws its water surface in, how many of them the `.TRG` covers, how many of THOSE its own still-water sheet covers (material 16), and the engine's own answer - the room left to the `.TRG` by fix round H's majority, or so many of its faces restored of so many, the ones under the `.TRG`'s own sheet being the difference. Then the **water frames**: the level's `.TEX` table read through the engine's own `HDScanLevelTextures`, the animated texture ranges the restored faces name, each frame's tile with the 64x64 cell it sits in, the HD `.DDS` that paints that cell and the rectangle inside it, the cell rule counted over the whole level (tiles with art, cells, tiles crossing a cell edge, cells wanting two files - the last must be 0), and a simulation of the classic rotation that reads back which HD page the face would show after each step. It is the offline twin of `BuildWaterFrames` in `hd_level.cpp`; both read the same file through the same reader.<br><br>**`-walk <seed room> <x y z>` runs the CLASSIC PORTAL WALK offline** (#123, fix round T3): `GetRoomBounds` and `SetRoomBounds` (`game\draw.cpp:3590` and `:3147`) carried over line for line, out of the classic `.TRC` handed in with `-roombox` - no device, no `.TRG`, no picture. It exists because the walk is the one part of the picture no renderer can show: it is arithmetic on the level's own portal records, and a `ROOMFLASH` line that says a room went missing cannot say what dropped it. The eye is in WORLD units and the tool prints which rooms' boxes hold it, so a log line can be handed to it as it stands. build made of them, so the two listings can be held against each other line for
line; `-window all|open|intruding` draws one half of every group, `-clipgroup
<group> <l,t,r,b>` puts a scissor round ONE group (which is what a portal
window really is, and what the whole-scene `-scissor` cannot do), and `-tround
<group> <l,t,r,b>` draws one group the way fix round T drew it - its inside
half inside the rectangle, its overhang whole - which is the "before" picture
of fix round T2.

One thing the two picture tools cannot make up: they have no classic level, so
`RoomProbe` cannot read a room's flags or its roomlets. `-underwater` and `-shimmer` are therefore
switches rather than answers, and `-shimmer` - and `-water` with it - lights or
wobbles the WHOLE room (the selector is aimed at the vertex's constant fourth
flag byte) where the engine touches only the vertices its own predicate marked.
That difference is large: over the vanilla levels the classic water set is 0 to
188 vertices per level, so a `-water` picture over-reports on purpose. The
picture proves the arithmetic and the animation; which vertices get it is the
engine's business and the play test's. The stage S5 scroll and wind are NOT in
that class - they are marked in the `.TRG` itself, so what the tool draws there
is what the engine draws.

`bshader` is not a tool but a build step of its own: it runs `fxc` from the
Windows SDK over `specific\hd\hd_shader\*.hlsl` and writes the bytecode next to
it as `.inc` byte arrays. The engine's project has **no** shader compile step.
Both the `.hlsl` and the generated `.inc` are checked in — GPLv3 wants the
source that produced the bytecode to sit beside it.

**`be.bat` now checks that for you** (#123, fix round G). Every `.inc` carries
the MD5 of the `.hlsl` it came from on its last line (`bshader.bat`, `:stamp`)
and `be.bat` compares the two before it builds; where they differ it prints
`be: regenerating shaders - ... out of step with the HLSL`, runs `bshader.bat`
itself and only then builds, and it refuses to build at all if that fails. A
**content** stamp and not a file date, because a fresh clone gives every file
the same date and a date guard would then either cry wolf or say nothing at
all. It exists because round R3b changed `hd_room.hlsl`, never ran `bshader`,
and shipped a build whose source and whose picture disagreed - nothing in the
tree could say so, and it took a play test and two fix rounds to find. Running
`bshader.bat` by hand still works and is still the right thing to do while
iterating on a shader; the guard is the net underneath.

## The other half: the engine tells you things too

The engine writes nothing unless it is started with `-log`. `Log.bat` in the
release package does exactly that, which is why it is in there. The seams
below are permanent - they are not debug leftovers to be tidied away, they
are how a player's crash report becomes usable.

| Symptom | Seam | What it prints |
|---|---|---|
| the wrong sound plays | `SFXLOG` | which sample really played, and which anim command asked for it |
| an enemy is invisible | `SLOTLOG`, `SKIPLOG`, `MESHLOG`, `CLIPLOG` | the four separate reasons: no free AI slot, control skipped it, no mesh, clipped away |
| ...and if it is the clipping | `CLIPDETAIL` | the actual window and the camera it was measured against |
| an item is in the wrong place, or vanishes | `ITEMLOG` | slot, room, OCB, flags per item at load |
| ...and something moves it later | `ITEMWATCH` | who wrote which room number, and when |
| the outfit looks wrong, a limb is misplaced | `SKINLOG` | the skin's bone stack |
| the first-person view sits wrong | `FPHEAD`, `ALTERFOV` | the head bone per frame, and the field of view |
| an HD object or Lara is wrong, or classic when it should not be | `HDLOG` | per level: which slot got which model and why it was refused; Lara's outfit, her parts and the reason for a classic one. Per level's first HD frame: `itemcheck` and `lightcheck` for the objects, `laracheck` and `braidcheck` for Lara |
| it stuttered, or dropped under the frame rate | `FPSLOG` | one line per second: frames presented, the longest gap, and `logic_ticks=` - what the SIMULATION ran, which must stay 30 whatever the frame rate is (#148) |
| ...and *why* it stuttered | `PROFLOG` | the same second split into the fifteen phases of a frame (logic, room walk, HD rooms, HD objects, buckets, sort, the wait for the slot, `Present`), mean and worst; plus one line for **every** frame that missed its slot with all its phases, and one `first_frame` line per level (#148) |
| at *Frame rate 60* the motion is no smoother than at 30, or something jerks | `INTERPLOG` | one line per LOGIC second: how many frames were interpolated, how far Lara moved per drawn picture (must HALVE against a 30 Hz run over the same walk), how many things really moved, and every deliberate snap by cause - teleport, room jump, camera cut, cut scene (#148, order 2) |
| the first seconds of a level are rough | `WARMUP` | one line per load: how many texture pages and buffers were made resident before the first frame instead of inside it (#148) |

`SLOTLOG` also prints `MAX_LOT`, which is the number that decides how many
enemies can be active at once - see `Tomb5 Limits\Limits.txt`.
