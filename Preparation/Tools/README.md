# The tools, and which one answers which question

Fifty-two diagnostic tools sit in `Diagnose\`, forty-three of them with a
build script beside them. This page is their index: the way to find the
right one without already knowing it exists.

Every tool prints its own usage when started without arguments, and every
one carries a header comment saying why it was written. That header is the
authority; this page only points at it.

## Building

`Diagnose\<b*.bat>` - run it, it builds in place. Every script is relative to
its own folder, so a fresh clone builds them. They need Visual Studio with
the C++ workload; the path to `vcvars` is the one absolute thing in them.

`bmap.bat` and `btrg.bat` are no exception: every path in them is the
`%~dp0` form as well.

**The one prerequisite, said once here:** the `vcvars` line names a specific
Visual Studio installation. If yours sits elsewhere - a different edition, a
different major version - that single line in each script is what to change;
nothing else in them is machine-dependent. Two of the forty-five `b*.bat` are
not tool scripts at all: `be.bat` builds the engine and `bshader.bat` compiles
the shaders.

Nine tools have no script and are built by hand from their header comment:
BoneCheck, CornerCheck, DinoCheck, FaceCheck, GeomTest, TR3FetchCheck,
TR3SoundCheck, TriggerCommands, WinCheck.

CornerCheck, GeomTest and WinCheck were written in a scratch folder outside
the clone, and their build scripts stayed behind on purpose: those carried
absolute paths, and two of them were even named `bcc.bat` and `bwc.bat`,
which belong to CameraCheck and BalanceWriteCheck here. All three take the
same command line as CameraCheck's script - `Tr5Level.cpp` plus zlib, nothing
else - with their own name substituted.

The `step=`/`kept=` line of the wrap and grab tables also prints `d_off=`, `today=` and `narrowed=` in words (`blends` or `stands down`) and `worst=`, the difference the two pictures grow to over a whole tween - which is the largest one, not the alpha-0.5 pair printed beside it; the verdict is printed in words so that it is never inferred from the absence of a marker on cases where neither rule fires. |

**Savegames**
| Tool | Script | What it answers |
|---|---|---|
| `SaveDiff` | bsd | two savegames compared **field by field, by name**. Prints `IDENTICAL` when the files match to the byte, otherwise one line per differing field with both values - so "played four seconds longer" (`Game.Timer`, the clock, Lara's position) is told apart at a glance from "the game ran differently" (`Level.Kills`, the ammunition counts, `Lara.air`). Written for the frame-rate proof: the draw path has its own RNG that the simulation never reads, so the same seed and the same inputs must arrive at the same state at 30 and at 60 frames a second, and a savegame is that state written down. The recipe is in `docs/Engine-Manual.md` under *Frame rate*.<br><br>Takes every offset from the engine's own `global/types.h` with `offsetof`, so it cannot go stale - and is therefore built **x86**, like `BalanceCheck` and `RoomProbe`: the structs are `#pragma pack(1)` but carry pointers, and a pointer is four bytes in the engine. What it cannot name is the savegame *stream* inside `SAVEGAME_INFO::buffer` - that is what `WriteSG` (`game/savegame.cpp`) packed in a variable-length, conditional order - so those are reported as differing byte runs with their offset. |
| `InterpTest` | bit | the ARITHMETIC of the 60 FPS interpolation, checked with no game, no level and no device. It **includes the engine's own `TOMB5 Code\TOMB5\game\interpolate_math.h`** rather than a copy of it, so it cannot drift from what the engine does: a change to the lerps or the snap thresholds is a change this test sees. 729 checks — the count the run itself prints, and the one at the end of this row — the short-angle lerp over a sweep of 16,256 angle pairs (that every one turns the SHORT way round and lands within a unit of halfway, with the 128 exact half-turns stepped over and asserted on their own), the position lerp over the whole coordinate range of a level, the snap thresholds against the engine's own speeds (a terminal fall interpolates, a sector-wide teleport does not), that a Manhattan sum is never smaller than the true distance, and the cadence: `framecount` and `DrawPhaseGame`'s alpha rule run for a simulated minute at both frame rates and through a hitch - 1800 logic ticks either way, exactly half the frames interpolated at sixty, none at thirty, every drawn step exactly half a tick.<br><br>It exists because a short angle blended the LONG way round is invisible almost all the time and looks like a rendering glitch when it is not: one enemy, facing roughly south, spinning backwards for half a tick on every second frame. That has to be proven at the wrap, and a play test will not put a body on the wrap when you want it to. `counters` is a simulated wall-clock second at both rates with the engine's own tween-frame rule, asserting that a guarded counter steps thirty times in BOTH modes (not sixty), that the nine-step screen fade spans the same nine ticks - 2n-1 presents at sixty, because it begins and ends on a live frame - and that at `fps_mode 0` not one frame is ever an in-between frame. Ten simulated seconds at 60, 120 and 144 Hz each run **300 logic steps** against 600, 1200 and 1440 frames; the blend factor is **never clamped** (a clamp means a frame asked for a state the logic has not computed, and the picture stands still for it); no frame draws what the one before it drew; exactly one frame per logic tick carries the per-frame counters, which at these rates cannot be `alpha < 1`; and what is drawn tracks the wall clock with a spread under 1e-7 ticks, which is a float's precision and not drift. The identity is also swept over every step a TR5 particle can carry, in both signs, against the obvious rearrangement `cur - step * (1 - alpha)`, which disagrees on 16,384 of the 40,965 pairs - that is the rounding trap the engine's form avoids, and it is printed rather than described. `camera_aim` and `title_cadence` are both faults a play test found written down as arithmetic. `camera_aim` runs the OLD target rule beside the new one over a swept first person camera whose target sits at the engine's own `0x5100`: the old rule cuts on a three degree head turn - under it `INTERPLOG` reads `camcut=10..17` a second with Lara standing still - and the new one cuts on no turn up to twenty degrees a tick in either axis with the eye moving as well (over 500 cases), still cuts at sixty, ninety and a hundred and eighty degrees, leaves a chase camera alone, still catches a target jumping two sectors, and hands a near target back as its own offset to the unit. `title_cadence` runs the title menu's own two-ticks-a-present accumulator from both parities: at two ticks `framecount += 2; while (> 0) tick, -= 2` RETURNS TO WHERE IT STARTED, so a title entered on -1 stayed on -1 and the old rule made every one of its frames an in-between frame - which stopped the screen fade, left `DoFade` at 1 and put a black quad over the menu for ever. answer together, and they must answer it the same way. `TrgProbe -roomspace
-classic <folder holding the classic .TRC>` reads the classic level and the
`.TRG` side by side and prints the room boxes, the OVERLAP list - whose art
stands inside whose room's own inside, with no portal between the two, each

room apart (box, portals, vertical links, whose art is inside it), `-statics` /
`-slot <n>` every static mesh with how much art stands in its box, `-slack` and

listing is never mistaken for the engine's), and `-near <x> <y> <z> <radius>` says
whose art stands at a given

how "a tower that is in no room's box" was turned from a guess into a number.

build made of them, so the two listings can be held against each other line for
line; `-window all|open|intruding` draws one half of every group, `-clipgroup
<group> <l,t,r,b>` puts a scissor round ONE group (which is what a portal
window really is, and what the whole-scene `-scissor` cannot do), and `-tround
<group> <l,t,r,b>` draws one group the OLDER way - its inside
half inside the rectangle, its overhang whole - which is the "before" picture
next to the current one. `-roomwin <g>:<l>,<t>,<r>,<b>[;...]` hands named

`DrawRoomWindowed` does, and `-decide whole|scissor|frame|face` says how the

with one `decide:` line per piece, which ends in `inner` for a piece that

One thing the two picture tools cannot make up: they have no classic level, so
`RoomProbe` cannot read a room's flags or its roomlets. `-underwater` and `-shimmer` are therefore
switches rather than answers, and `-shimmer` - and `-water` with it - lights or
wobbles the WHOLE room (the selector is aimed at the vertex's constant fourth
flag byte) where the engine touches only the vertices its own predicate marked.
That difference is large: over the vanilla levels the classic water set is 0 to
188 vertices per level, so a `-water` picture over-reports on purpose. The
picture proves the arithmetic and the animation; which vertices get it is the
engine's business. The scroll and wind are NOT in
that class - they are marked in the `.TRG` itself, so what the tool draws there
is what the engine draws.

`bshader` is not a tool but a build step of its own: it runs `fxc` from the
Windows SDK over `specific\hd\hd_shader\*.hlsl` and writes the bytecode next to
it as `.inc` byte arrays. The engine's project has **no** shader compile step.
Both the `.hlsl` and the generated `.inc` are checked in — GPLv3 wants the
source that produced the bytecode to sit beside it.

**`be.bat` checks that for you.** Every `.inc` carries
the MD5 of the `.hlsl` it came from on its last line (`bshader.bat`, `:stamp`)
and `be.bat` compares the two before it builds; where they differ it prints
`be: regenerating shaders - ... out of step with the HLSL`, runs `bshader.bat`
itself and only then builds, and it refuses to build at all if that fails. A
**content** stamp and not a file date, because a fresh clone gives every file
the same date and a date guard would then either cry wolf or say nothing at
all.

**`be.bat` also compiles the whole engine on every run** (`msbuild
/t:Rebuild`, about half a minute), never only what `msbuild` takes for
changed. `msbuild` goes by file dates: a source file put back with a date
older than its object file - a copy that keeps the date, an archive unpacked
over the tree - is passed over although its content is new, and the link
joins object files of two states of one header. Such a binary compiles, links
and can die at once. The full build leaves no such mix possible, and it gives
every binary its own build time (`winmain.cpp` writes it as the first line of
a `-log` run).

**And a content stamp has its own trap.** An MD5 is taken over bytes, and
line endings are bytes: with
git's Windows default the `.hlsl` came out of a fresh clone with carriage
returns the stamped file never had, so the guard fired on shaders that were
perfectly in step, rebuilt them, and left two tracked files modified in a
clone nobody had touched. Worse, the two pairs disagreed with each other -
one had been stamped over LF, the other over CRLF - so on any machine one of
them was lying. The fix is one rule in `.gitattributes`, `eol=lf` for
`**/hd_shader/*.hlsl` and `*.inc`, so every machine hashes the same bytes;
the four `.inc` were regenerated over LF sources and proved to differ from
their predecessors in the stamp line alone. Nothing in the scripts changed.
If you edit a shader, keep its file LF. It exists because a shader source
once changed without `bshader` being run, and the build shipped with its
source and its picture disagreeing - nothing in the tree could say so, and it
took a play test to find. Running
`bshader.bat` by hand still works and is still the right thing to do while
iterating on a shader; the guard is the net underneath.
